# 企业内部设备借用工单系统 · 功能与流程说明

> 版本基线：**V51**（Flyway 最高迁移） · 文档日期：2026-10-16
> 适用读者：系统管理员、IT 运维、业务管理员、验收方

---

## 一、系统概览

| 项 | 说明 |
| --- | --- |
| 定位 | 企业内部设备借用 / 审批 / 交付 / 归还 / 报修的完整闭环系统 |
| 规模 | 约 100 名员工、1000 台设备 |
| 形态 | **单套响应式 Web**（PC 常驻侧栏 / 手机抽屉菜单），不做 PC、移动两套代码<br>**可作为 PWA 安装到桌面**（含 manifest 与多尺寸图标）；Capacitor 工程配置已就位（`capacitor.config.json`），未安装依赖、未发布原生包 |
| 技术栈 | Vue 3 + Vite 5 + TS(strict) + Element Plus + Vant ｜ Spring Boot 3.2.5 + JDK 21 + MyBatis-Plus + Flyway ｜ MySQL 8 + Redis 7 |
| 鉴权 | Cookie 携带 JWT（HttpOnly + SameSite=Lax）+ CSRF 双重防御 + Argon2id 密码哈希 |
| 部署 | 原生（Windows/Linux）或 **Docker Compose**（群晖 / 通用 Linux 服务器） |

**三条核心设计原则**

1. **权限目录即代码事实源** —— 权限码写在代码里（`PermissionCatalog`），不落库。避免「库里加了个码 → 界面勾得上 → 点下去不生效」。
2. **表单与流程可配置** —— 申请类型、动态表单、审批流程都由配置驱动，不改代码即可新增业务类型。
3. **演示数据只在开发环境出现** —— 生产启动即清空演示数据，避免凭空多出可登录账号。

## 二、角色与权限

### 2.1 六个内置角色

| 角色码 | 名称 | 定位 | 拿到的权限 |
| --- | --- | --- | --- |
| `super_admin` | 超级管理员 | 系统所有者，**不可修改、不可删除** | **全量**（由守卫短路放行，即使数据库授权行被误删也进得去） |
| `admin` | 管理员 | 业务管理员 | 工单/设备/组织人员/报表/监控/系统参数只读 等业务面 |
| `it_manager` | IT 主管 | 审批链上的管理层 | 普通员工全集 + 工单管理 + 资产管理 + 统计 |
| `it_executor` | IT 执行人 | 实际发设备/收设备的人 | 普通员工全集（设备交付确认会指派到具体执行人） |
| `dept_manager` | 部门经理 / 组长 | 某批人的直属主管 | 普通员工全集（差异不在权限码，而在**组织关系**——他的待办里真有单） |
| `user` | 普通员工 | 提交与查询自己的工单 | 提交申请 / 我的申请 / 待我审批 / 我的待处理 / 消息 |

> ⚠️ **全员都有「待我审批」**：审批人是按流程与会签/或签动态解析出来的，员工完全可能被指为某个节点的审批人，与角色无关。

### 2.2 权限码命名约定

```
<模块>:<对象>:<动作>        例：device:ledger:manage
动作只有三种：view（看） / manage（改） / import（批量导入）
```

刻意**不细分** create/update/delete —— 内网场景里「能改台账」与「能删台账」很难有真实差异，过细只会让授权界面变成没人愿意读的表格。

### 2.3 权限申请与自动开通

- 员工可在系统内**申请权限**；按 `permission_apply_policy` 判定**风险等级**：
  - **普通**（只读类）→ 一级审批（直属主管 / 部门主管）；
  - **高危**（全部 `*:manage` 写操作、`*:import` 批量、`order:force:manage`，以及**未识别的码**）→ 部门主管 → **超管** 两级。
- **提权类权限默认不开放申请**（拿了它就能绕过流程给自己提权）：角色维护、AD 管理、系统参数修改、在线升级的两个码。
- 审批通过后**自动开通**。
- 未知码按**高危**处理（保守方向：宁可让只读码多走一级，也不让写权限漏过一级）。

## 三、功能地图（按左侧菜单）

### 3.1 工作台（首页，不占菜单）

- 顶栏：待办统计、消息铃铛；
- 快捷入口：提交申请、我的工单、**扫码借还**；
- **扫码借还**（路由 `/scan`，刻意**不挂左侧菜单** —— 它是「站在设备前才会用」的动作，挂一级菜单只是噪音；入口放在工作台，也可把页面加到手机桌面直接打开）：三个动作「**借用 / 归还 / 查看**」，扫设备二维码后按角色与设备状态分流；设备无摄像头或未授权时**如实告知原因**并降级为手工输入编码；
- **统计仪表盘**（需 `dashboard:view`）：区间内工单量 / 类型 / 状态 / 时间 / 部门分布 + 平均审批时长 / 超时率。

### 3.2 审批中心 `/order`

| 菜单 | 权限码 | 说明 |
| --- | --- | --- |
| 提交申请 | `order:apply` | 两步选择：先选申请类型，再填表单（内置「借用设备」「故障报修」+ 自定义类型） |
| 我发起的申请 | `order:mine` | 查看自己提交的全部工单与进度 |
| 待我审批 | `order:approval` | 审批待办（**与「我的待处理」是两件事**） |
| 我的待处理 | `order:pending` | IT 执行人侧的**发放 / 回收**待办（"该我动手发设备"） |
| 全部工单 | `order:all:view` | 全局视图，仅管理端 |
| （操作）超管强制干预 | `order:force:manage` | 驳回 / 终止 / 转交审批 / 转交执行人 |

### 3.3 资产管理 `/asset`

| 菜单 | 权限码 | 说明 |
| --- | --- | --- |
| 设备台账 | `device:ledger:view` | 设备清单、详情、二维码标签打印 |
| 设备分类管理 | `device:category:manage` | 分类维护 |
| 设备故障记录 | `device:fault:view`（**报修处理人额外可见**） | 汇总上报 / 台账登记 / 归还登记三类故障 |
| 设备盘点 | `inventory:view` | 盘点任务（新建 / 核对 / 完成），报告中的「盘亏」即台账数据 |
| （操作）台账维护 | `device:ledger:manage` | 新增 / 编辑 / 状态流转 |
| （操作）设备批量导入 | `device:import` | 模板下载 → 预览校验 → 确认导入 → 失败明细 Excel |

### 3.4 组织与人员 `/staff/organization`

**三合一页面**：员工档案 + 部门（业务分组）+ 最终处理小组，收进「左部门树 + 右成员列表」。

| 操作 | 权限码 |
| --- | --- |
| 进入页面（只读） | `staff:view` |
| 员工维护（新增/编辑/重置密码/离职） | `staff:manage` |
| 员工批量导入 | `staff:import` |
| **部门维护**（新增/编辑/移动/设主管/删除） | `department:manage`（**仅超管**） |

> ⚠️ `department:manage` 刻意不给 admin：部门是**审批上级的事实源**，动一个部门主管等于改一批人的审批路径。可做到「业务管理员能维护员工，但只有超管能改组织结构」。

### 3.5 消息中心 `/message/list`

站内消息：审批通知、交付/归还提醒、到期预警、故障通知、绑定/改密告知、备份失败告警、异常登录告警等。支持批量删除。

### 3.6 监控与报表 `/monitor`

| 菜单 | 权限码 | 说明 |
| --- | --- | --- |
| 使用记录 | `usage:view` | 设备的领取 / 归还 / 流转历史 |
| 统计报表 | `asset:report:view` | 借用频次 / 审批时效 / 故障统计 |
| 流程监控 | `flow_monitor:view` | 模板工单量 / 平均审批时长 / **瓶颈节点** |
| 操作日志 | `log:view` | 谁做了什么（审计面） |
| 异常日志 | `exception:view`（**仅超管**） | 系统因为什么坏了（运维面） |
| 安全日志 | `security:view`（**仅超管**） | 登录失败 / 账号锁定 / IP 封禁检索与**人工解封** |

> 「监控与报表」的共性是**看系统跑得怎么样**；「系统设置」保留的是**配系统怎么跑**。

### 3.7 系统设置 `/system`

| 菜单 | 权限码 | 说明 |
| --- | --- | --- |
| 系统参数 | `config:view` / `config:manage` | 卡片式配置页，**改完热生效**，无需重启 |
| 角色与权限 | `role:view` / `role:manage` | 自定义角色 + 权限勾选树 |
| AD 域控配置 | `ad:view` / `ad:manage` | 仅超管（含服务账号密码，决定"谁能进系统"） |
| 主备配置 | `ha:view` / `ha:manage` | 仅超管（节点登记 / 手动切换 / 立即同步） |
| 在线升级 | `system:upgrade:view` / `:execute` | 仅超管（升级接口等价于代码执行能力） |
| 备份记录 | `backup:view` / `backup:manage` | 自动/手动备份与记录 |
| 申请类型与流程 | `apply_type:view` | 左边配表单、右边配审批流程，**一个页面搞定** |

> **可见性规律**：基础设施级权限（AD / 主备 / 在线升级 / 备份 / 异常日志 / 安全日志）**一律不下发给业务管理员** —— 它们需要的基础设施能力（改 `.env`、进 NAS、看容器日志）admin 并不具备。

## 四、核心业务流程

### 4.1 借用闭环（主流程）

```
① 提交申请           ② 多级审批            ③ 交付             ④ 使用          ⑤ 归还              ⑥ 确认收回
员工填表单     →   会签 / 或签逐级    →   执行人发设备   →   计时开始   →   申请人发起归还   →   执行人确认收回
   │                   │                     │                  │                │                    │
生成审批快照      审批人动态解析       最终处理小组         到期自动顺延       归还条件登记        设备回 AVAILABLE
                                       随机分配执行人       最多 2 次          有无损坏/丢失
```

| 环节 | 关键机制 |
| --- | --- |
| **提交** | 生成**审批快照**（此后改流程模板不影响已提交的单）；申请时校验设备可借状态 |
| **审批** | 审批人按节点类型解析：直属主管 / 部门主管 / 指定角色 / 最终处理部门成员 / 申请人自选 / 上一节点指定；支持**会签**（全通过）与**或签**（任一通过） |
| **交付** | 工单到达「待交付」后，**最终处理小组内随机分配执行人**；执行人发放并确认，设备转 `IN_USE` |
| **顺延** | 到期**不自动归还**；自动顺延最多 **2 次**；2 次之后超时，**执行人可直接收回** |
| **归还** | **两步走**：申请人发起 → 执行人确认收回；登记归还条件（正常 / 损坏 / 丢失） |
| **转交** | 审批人可转交他人；离职自动转交其待办 |

**工单状态机**

```
PENDING_APPROVAL(审批中) → PENDING_DELIVERY(待交付) → BORROWED(使用中)
      → PENDING_RETURN(待收回) → RETURNED(已归还) → COMPLETED(已完成)
旁路终态：REJECTED(已驳回) / CANCELLED(已撤回) / TERMINATED(已终止)
```

**设备状态机**

```
AVAILABLE(可用) ──申请──> IN_APPROVAL(审批中) ──通过──> IN_USE(使用中)
      ↑                                                     │
      └──── 归还确认 ──── 待收回 ←──────────────────────────┘
      ├─ LOCKED(临时锁定)      ├─ MAINTENANCE(维修中)      ├─ LOST(已丢失)      └─ SCRAPPED(已报废)
```

### 4.2 故障报修处理流程（**不是审批流**）

```
上报(台账登记/归还登记/直接上报) → PENDING_REPAIR(待处理) → IN_PROGRESS(处理中) → REPAIRED(已修复)
                                                              └→ UNREPAIRABLE(无法修复)
独立终态：SCRAPPED(已报废)   ← 由资产管理员决策，与维修结论是两件事
```

- **通知谁 = 谁能接单**：两者同源（`FaultRepairSettings` + `FaultRepairAssigneeResolver`）。
- 「**无法修复**」≠「**已报废**」：无法修复时**设备状态不变**（仍 `MAINTENANCE`），等资产管理员决定是否报废。
- 报修处理人（维修人员）**不需要管理员权限**：准入走「处理流程范围」，服务端对非管理员强制只返回「未完结 且（没人接单 或 由他接单）」的数据。

### 4.3 延期

借用到期前可申请延期，生成**延期子单**，走独立审批；审批通过后顺延到期时间。

### 4.4 催办与催还

- **催办**：审批人可催当前节点；
- **催还**：到期未归还时执行人可催还；
- 均落站内消息并记审计。

### 4.5 超时与自动任务

| 定时任务 | 作用 |
| --- | --- |
| 到期预警 | 到期前提醒申请人与执行人 |
| 自动顺延 | 到期未还自动顺延（最多 2 次） |
| 超时告警 | 超时未还通知执行人 |
| 审批超时提醒 | 节点超时提醒审批人 |
| 设备工单对账 | 设备状态与在途工单核对 |
| 附件孤儿清理 | 清理无主的附件文件 |
| 导出过期清理 + 僵尸任务回收 | 释放存储与卡死任务 |
| 数据库自动备份 | 每日全量备份 + 失败上报（不静默） |
| AD 用户同步 | 按需（手动 / 定时）从域控同步账号 |

### 4.6 离职联动

员工离职时：其待审批 / 待处理任务**自动转交**给指定人（或主管），并在消息与审计中留痕。

## 五、权限与安全

### 5.1 登录与账号

- **用户名（企业内即姓名）登录**，密码 Argon2id 哈希；
- 超级管理员通过**环境变量种子化**创建，**首次登录强制改密**；
- 支持**手机 / 邮箱找回密码**（两步：验证码 → 重置），首次登录可能要求**绑定联系方式**。

### 5.2 安全防护

| 机制 | 参数（可在系统参数中调整） |
| --- | --- |
| 登录失败锁定 | 连续失败 5 次 → 锁定 30 分钟 |
| 账号维度限流 | 每分钟 3 次 |
| IP 维度封禁 | 失败 10 次 → 封禁 30 分钟（两级封禁策略） |
| 异常登录通知 | 凌晨登录 / 新设备 / 非常用 IP → 站内消息 + 邮件 |
| 可信代理 | 收紧 XFF 解析，防止伪造来源绕过限流 |
| 内网白名单 | 可配置，默认已给出安全默认值 |
| 验证码渠道 | 短信 / 邮件，未配置完整时**如实告知原因**并退回日志渠道（不静默失败） |

### 5.3 审计

- **操作日志**：谁做了什么（含 MDC traceId）；
- **异常日志**：未捕获异常与堆栈；
- **安全日志**：登录失败 / 锁定 / 封禁与人工解封；
- 配置变更、密码重置、权限变更、强制干预等**高危动作**单独留痕。

## 六、运维能力

### 6.1 数据库备份（P0）

- 每日**全量备份**，落在 `BACKUP_DIR`（建议指向另一块物理盘——同盘不算备份）；
- 备份失败**必须上报**（站内消息，不静默）；
- 页面可**手动触发**并查看历史记录。

### 6.2 主备双机（`deploy/ha/`）

- 提供 MySQL 复制、Redis 哨兵、keepalived VIP、共享附件目录的**完整脚本与模板**；
- 页面可登记节点、手动切换、查看心跳与同步状态。
- ⚠️ **本系统按拍板不引入自动接管**：故障后需要手工或脚本切换 DNS / 虚拟 IP。页面会如实写出这一点。

### 6.3 在线一键升级（V49 → V51）

**两个入口常显、各自独立开关、默认都关闭**：

| 入口 | 开启后可用性 | 说明 |
| --- | --- | --- |
| **一键在线升级** | 需**运维代理（ops-agent）就绪** | 由侧车执行 `docker compose pull` + `up -d --force-recreate backend frontend` |
| **上传升级包** | 非 Docker 部署时用 | 容器跑的是镜像，上传的 jar/dist 落进宿主目录**不会被加载** —— 页面会提示，并在「应用」时**显式拦截** |

机制要点：

- 开关存在数据库，**改完立刻生效**，不需要改 `.env`、不需要重建容器；两者互不影响；
- `.env` 的 `UPGRADE_ENABLED` 是**两个入口共同的总闸**（为 true 时页面开关强制打开并置灰）；
- 后端把升级请求写成 `ops-data/requests/<taskNo>.json`，侧车轮询执行，写回执到 `ops-data/upgrade/state/result/<taskNo>.json`；
- 升级期间页面显示 agent 的**实时进展**（正在拉镜像 / 正在重建容器 / 等待健康检查）；
- 任务终态以**回执**为准；无回执时用「当前版本 == 目标版本」兜底 —— 但**浮动标签（latest）下该判定不生效**（否则会恒真，把失败伪装成成功）；
- 升级**只在 backend / frontend 之间滚动**，数据库与缓存不动。

**侧车部署要点**（详见 `deploy/README.md`）：

```bash
cd /vol2/.../deploy
# DEPLOY_HOST_DIR 必须给出宿主绝对路径：否则 compose 的相对挂载会被宿主解析到别处
DEPLOY_HOST_DIR=$(pwd) OPS_UI_ENABLED=false \
  docker compose -f ops/docker-compose.ops.yml up -d --build
```

### 6.4 AD 域控（预留，已实现）

- 服务账号配置 + **DN 自动推导** + 一键测试连接；
- **AD 优先登录**：域账号走 AD 校验，超管仍走本地；AD 不可用时**降级**到本地；
- 用户同步（手动 / 定时），支持 AD ↔ 本地账号互转与「账号来源」筛选。

### 6.5 系统参数

卡片式配置页，按业务域分组，改完**热生效**。覆盖：站点名称与版权、联系方式、密码策略、登录与限流策略、附件与存储、导出保留天数、告警渠道（SMTP / 短信）、升级开关等。

### 6.6 首次部署向导（ops-agent 侧车）

全新安装时，在 `deploy/` 下起一个**独立侧车**（`ops-agent`）—— 它不依赖主栈、**不含任何必填变量**，
因此能在一份 `.env` 都不存在时先跑起来：

- 浏览器打开 `http://127.0.0.1:8090`：向导问几项（数据目录 / 端口 / 是否 HTTPS / 是否自动建超管）
  → 自动生成 `.env` → 拉起主栈 → 校验健康检查；
- 装完写 `.installed` 标记，此后**写接口一律拒绝**（410）；
- **安装完成后建议以 `OPS_UI_ENABLED=false` 重启侧车**，关掉这个入口 —— 它具备「重建整套容器」的能力；
- 端口默认只绑 `127.0.0.1`；`docker.sock` **只挂给这一个容器**，命令白名单只允许
  `pull` + `up -d --force-recreate backend frontend`，以非 root 运行，并写审计日志。

⚠️ **挂 `docker.sock` ≈ 把宿主 root 交给这个容器**（容器内 `docker run -v /:/host` 即等同）。
这是「自动 pull + 重建」无法回避的代价，因此只给它一家，其余服务一律不挂。

## 七、关键设计约定（踩过坑的规则）

| 约定 | 为什么 |
| --- | --- |
| **「某部门的成员是谁」只有一处实现**（`DepartmentService#activeMemberIdsOf` = 主部门 ∪ 兼职部门 → 在职过滤） | 曾有多处各自只查兼职表，导致候选集**恒为空且不报错** |
| **表名统一单数**，且不可用 `order` / `group`（MySQL 保留字） | V47 统一重命名 |
| **历史迁移脚本不可修改**（连注释也不行） | Flyway 校验和错误会直接启动失败 |
| SQL 清理一律 `DELETE`，**禁用 `TRUNCATE`** | 保留自增、保护演示数据 |
| 改 `system_config` **必须走接口** | 服务端有内存缓存，直接改库不会刷新 |
| 含表结构变更的版本**只能停机升级**，严禁新旧实例混跑 | 旧实例会报表不存在（1146） |
| **容器内的工具去操作宿主 Docker，绝不能使用相对路径** | 相对 bind 会被宿主 daemon 解析到不存在的目录，Docker 会**静默新建空目录** |
| **不要拿浮动标签做版本比对** | `latest == latest` 恒真，等于「无条件判成功」 |
| 前端三档断点 **≤767 / 768–1023 / ≥1024**，CSS 与 JS 必须同步 | 不同步会出现「桌面尺寸却按平板收起侧栏」的互斥状态 |

## 八、部署与升级

### 8.1 环境要求

| 组件 | 版本 |
| --- | --- |
| JDK | 21（Adoptium / Temurin） |
| Node.js | 18+（推荐 20/22，仅本地开发/构建需要） |
| MySQL | 8.0.x |
| Redis | 7.x |
| Docker（可选） | 24+ + Compose v2 |

### 8.2 三条部署路径

| 路径 | 适用 | 关键步骤 |
| --- | --- | --- |
| **Docker Compose（推荐）** | 群晖 / 通用 Linux | `bash scripts/init-env.sh` → `bash scripts/preflight.sh` → `docker compose pull` → `docker compose up -d` |
| **原生部署** | Windows / Linux 直跑 jar | 建库 → 启 Redis → `java -jar ticket-system.jar` → Nginx 托管前端 dist |
| **主备双机** | 高可用要求 | 见 `deploy/ha/` 与 `DEPLOY.md` |

### 8.3 部署要点（易踩）

- `.env` 由 `scripts/init-env.sh` 一键生成（自动填 4 个随机密钥 + 问出 `COOKIE_SECURE`）；
- **`COOKIE_SECURE`**：挂 HTTPS 反代填 `true`；用 `http://<IP>:<端口>` 访问必须 `false`，否则表现为「登录返回 200 却立刻弹回登录页」；
- **国内网络拉不动 `ghcr.io`**：在 `.env` 里加一行 `REGISTRY=ghcr.nju.edu.cn` 即可，**不要改 compose 文件**（那会变成长期未提交的本地改动，挡住每一次 `git pull`）；
- **权限**：`deploy/` 下不能有「其他用户可写」的文件 —— MySQL 会**拒绝读取**这类配置文件（`my.cnf` 于是静默失效）。`preflight.sh` 会自动收权；
- **镜像更新三步**：`docker pull` → 校验镜像 ID/`created` → `up -d --force-recreate <服务>`。`docker compose up -d` **不会**因 `:latest` 内容变化而重建容器；
- 升级前可用镜像标签自证版本：`docker image inspect -f '{{index .Config.Labels "org.opencontainers.image.revision"}}' <镜像>`。

### 8.4 环境变量（关键几项）

| 变量 | 说明 |
| --- | --- |
| `DATA_ROOT` | 数据根（附件 / 导出 / 日志 / 备份） |
| `MYSQL_ROOT_PASSWORD` / `REDIS_PASSWORD` / `JWT_SECRET` / `INTERNAL_ALERT_TOKEN` | 四个必须随机的密钥 |
| `COOKIE_SECURE` | 见上 |
| `WEB_PORT` / `TZ` | 对外端口 / 时区 |
| `IMAGE_TAG` | 镜像标签（留空即 `latest`；填 `commit-<短sha>` 可锁定版本） |
| `REGISTRY` | 镜像仓库（默认 `ghcr.io`，国内可换镜像站） |
| `UPGRADE_ENABLED` | 在线升级的**总闸**（生产默认 false；页面两个开关另受数据库控制） |
| `UPGRADE_OPS_DIR` / `UPGRADE_STORAGE_ROOT` | 与侧车共享的目录（compose 已自动接线） |
