## 二、关键决策与理由

### D-9.1 借用单只声明「类别 + 型号」，不绑具体资产

- **为什么**：需求方拍定「审批阶段不该占住一台具体设备」。绑定推迟到 IT 交付扫码那一刻，
  设备从 `AVAILABLE` 直接进 `IN_USE`，中间不再经过 `LOCKED / IN_APPROVAL`。
- **连带删除**：`device.locked_by / locked_at / lock_token` 三列、`POST /api/devices/{id}/lock` 等三个端点、
  `DeviceLockReleaseJob`、前端整段倒计时。**留着会误导**：一套算不出结果的倒计时比没有更糟。
- **交付是必要闭环**：不绑设备的单在交付时必须指定「发哪一台」。
  前端按申请口径预过滤（一级必匹配；二级 / 型号填了才校验），真正的裁决仍在后端
  `resolveDeviceForDelivery`（三层校验：分类 → 型号 → 空闲）。

### D-9.2 `device.model` 原列保留（`model_id IS NULL` = 待整理）

- 存量一千多条 `model` 是自由文本（`ThinkPad X1 / thinkpad x1`），迁移进字典后**无法保证无损**。
  保留原文可回溯、迁移可回滚；新逻辑一律不读 `model` 做比对。
- 台账页对未归类的设备显式回显「台账原型号文本：xxx（未归入字典）」。

### D-10.1 负责人 ≠ 借用人

- `device.owner_id` = 资产归属责任人（长期固定，`device:ledger:manage` 维护）；
  借用人 = `borrow_order.applicant_id`（动态）。
- **不冗余 `owner_name`**：姓名会改，冗余列必然出现「档案里是新名、台账里是旧名」。
  列表统一 id → name 批量解析。

### D-10.2 「我名下的设备」= 我负责的 ∪ **我正在用的**

- 原文只说「`owner_id = 当前用户`」。但负责人通常是 IT，若只查负责人，**普通员工看到的是空列表**——
  「我今天借的笔记本坏了」这条最常见诉求会找不到入口。
- 实现上两类并集，`toLookup` 是两模式唯一的「能不能报」判定口径：
  - `AVAILABLE` ⇒ 可报，走台账登记（无 `orderId`），报修后设备 `可用 → 维修中`；
  - `IN_USE` 且**是我的单** ⇒ 可报并带 `orderId`，设备保持使用中（去向由归还登记决定）；
  - `IN_USE` 他人 / `MAINTENANCE` / `SCRAPPED` / `LOST` ⇒ 不可报，且给出**能照着做**的原因。
- **一处 bug 修复**：`categoryNameMap` 在「一个分类 id 都没有」时返回 `Map.of()`，
  而不可变集合 `get(null)` 会 NPE —— 未归类设备会让整个下拉接口 500。
  已改为 `categoryNameOf(...)` 显式 null 短路（`toVO` 曾踩过同类坑）。

### D-10.3 无工单登记对普通员工开放，护栏改为「设备必须可用」

- 「公共设备」模式的定义就是「没有负责人的设备」。若仍要求管理员，入口等于不存在。
- 真正的护栏是**状态**：使用中的设备必须走工单路径，否则设备会绕过借用单被改成维修中，
  那台设备的工单永远收不回来（`FAULT_DEVICE_STATE_INVALID`）。
- 相应两个旧用例已改写：`report_ledger_byEmployee_movesAvailableToMaintenance`（放开后应成功）
  + `report_ledger_byEmployee_deviceInUse_rejected`（状态护栏仍在）。

### D-10.4 批量设置负责人是必需的，不是便利功能

- 存量 `owner_id` 全为 NULL。「我名下的设备」的唯一数据来源就是这个字段 ⇒
  没有批量回填，功能上线即空壳。
- 端点 `POST /api/devices/batch/owner` **只写 `owner_id` 一列**（不复用单条 `update`：
  那是整体替换语义，会把品牌 / 型号 / 存放位置一并清空）。
- `ownerId = null` = 清空（转为公共设备）。悬空 id 在服务层拒绝（`PARAM_INVALID`）：
  悬空 id 不报错，表现是「这台设备在报修页永远不出现」，事后极难定位。
- 单条 create / update 同样补了 `assertOwnerExists`。

### D-10.5 导入模板加「负责人账号」列，追加在末尾

- 解析是**按位置**的（用户常改表头文案）。插在中间会让旧模板整行错位且不报错；
  追加末尾则旧文件仍逐列正确，读不到即 NULL（= 未指定）。
- 填**登录账号**而不是姓名：姓名会重名，重名的表现是「设备悄悄挂到别人名下」。
  账号不存在 / 已停用离职 ⇒ 该行判失败并说明「请填写登录账号（不是姓名）」，**绝不静默忽略**。

### D-10.6 附件限额按业务类型拆分（R2 定稿）

- 旧：全局 `attachment.max-size-mb`（部署配置）同时管借用附件与故障照片 ⇒ 想放宽照片就得连带放宽长期留存的附件。
- 新：系统参数 `attachment_fault_photo_max_mb` / `attachment_apply_attachment_max_mb`（各默认 10，区间 1~100）。
  - 故障照片走前者，**其余一律走后者**（新增业务类型默认落在较严一侧，不会悄悄继承放宽过的照片限额）；
  - 配成 ≤ 0 时回落部署配置（0MB 会拒掉**所有**上传，那是配置坏了，不是策略收紧）；
  - 上限 100MB 与 Cloudflare 免费版单请求上限对齐，避免「参数说能传、网关先拒」。

## 七、风险与注意

- **升级顺序**：V56 含删列（`device.locked_*`），属结构变更 ⇒ 只能停机升级；V58 可热升级。
- **照片上限调大前**：必须同步确认边缘 Nginx `client_max_body_size` 与 Cloudflare 隧道上限，
  否则表现为「参数改了、上传直接失败」。
- **负责人批量回填**：建议先按部门小批量试，确认「我名下的设备」下拉符合预期后再全量。
- `device.model` 与 `model_id` 双列并存：任何新逻辑**不得**再读 `model` 做比对。
