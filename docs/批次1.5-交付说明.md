## 二、四个关键设计决策（都有理由，不是随手写的）

| 决策 | 为什么 |
| --- | --- |
| **模板留空 ⇒ 回落代码里的默认文案**（初值不预置） | ① 升级后行为与升级前**逐字一致**（零回归）；② 默认文案只有一份（在代码里），不会出现「库里一份、代码一份，改了不同步」；③ 管理员清空输入框即「恢复默认」 |
| **未知占位符原样保留** | 管理员把 `{code}` 写成 `{Code}` 时，邮件里会显示 `{Code}` —— 一眼看出笔误。若静默替换成空串，表现是「邮件里凭空少了一段」，排查成本高得多 |
| **主题强制清除换行与控制字符** | 主题属于**邮件头**：粘贴一段带换行的文本即可造成**邮件头注入**（往邮件里塞额外头部）。这是邮件功能最典型的安全坑，必须在渲染层兜住 —— 且**对渲染结果再净化一次**（占位符取值本身也可能带换行） |
| **发给普通员工的业务通知邮件不套告警模板** | `sendAlert` 的另一个调用方是 `UserNotificationService`（「你的工单已通过」这类）。给它套上告警模板会给普通通知带上 `[P0]` 语义与运维落款 —— 两者受众与语义都不同。因此**保留原方法不动**，另开 `sendAlertTemplated` 给运维告警 |

### 顺带：放宽列宽是必须的

正文模板很容易超过 `VARCHAR(512)`（几行中文就 200+ 字符）。**若不改列，保存超长模板会被静默截断** —— 截断不报错，是最难察觉的一种数据损坏。

## 三、过程中被既有护栏拦了两次（说明护栏是有效的）

| 拦我的不变式 | 我漏了什么 | 处置 |
| --- | --- | --- |
| `SystemConfigCatalogTest.everyItemHasRule` | 新增的 4 个参数**没配取值规则** ⇒ 该键不受任何长度校验 | 在 `ConfigRules` 补 4 条规则 |
| `typeMatchesRule` | 规则类型必须与控件类型一致 | 确认 `TEXT` ↔ `Kind.TEXT` ✅ |
| （我自己发现的） | 全局文本上限 `MAX_TEXT_LENGTH=500`，**正文模板装不下** | 正文规则显式给上限，且**与渲染层截断阈值对齐**（`MailTemplateRenderer.MAX_BODY_LENGTH`）—— 若规则比渲染层宽，会出现「库里存得下、发出去却被截断」，管理员会以为「改了没生效」 |

> 另外确认了一件事：`Rule.secretSized()` 只看「是否给了显式上限」，**不涉及加密或掩码**（它只用于挑前端 maxLength），所以模板不会被当成密文处理。

| 轴 | 结论 |

| **功能** | 验证码邮件与告警邮件的主题、正文均可后台自定义；配置页可编辑、可预览、可用「发送测试邮件」看真实效果；留空即恢复默认 |

## 六、验收路径

1. 超管登录 → **系统设置 → 系统参数** → 「通知与验证」卡片 → **邮件模板**分区；
2. 四个输入框应为**多行文本域**（可换行、自动增高）；
3. 把验证码正文改成例如：
   ```
   您好，本次验证码是 {code}，{minutes} 分钟内有效。
   —— {siteName} 技术支持
   ```
   保存后点「**发送测试邮件**」：
   - 邮件返回内容里应有「**用当前验证码邮件模板渲染出来的样子**」预览段；
   - 用真实验证码走一次「忘记密码 → 邮箱收码」，邮件正文应与模板一致；
4. 把正文**清空**再发一次 ⇒ 邮件回到系统默认文案（证明「清空即恢复默认」）；
5. 把主题故意写成带换行的两行 ⇒ 收到的邮件主题是**单行**（换行被净化，防头注入）；
6. 占位符写成 `{Code}`（大小写错）⇒ 邮件里**原样显示 `{Code}`**（能看出笔误，而不是静默少一段）。
